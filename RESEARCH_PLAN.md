# План ресерча: `plant-manager-prod` в LangSmith (последние ~6 недель)

Проект: `plant-manager-prod` (id `921e369c-2274-49b4-a496-48954fba55d0`), граф `graph_regular_check` из `langgraph-app/lg_main/g_regular_check/graph.py`. Запускается каждые 4 часа через Heroku Scheduler → `runner.py`.

Доступ: `langsmith` CLI, ключ уже в `.env` (`LANGSMITH_API_KEY`). Базовая команда:
```
export LANGSMITH_API_KEY=$(grep LANGSMITH_API_KEY .env | cut -d= -f2)
langsmith run list --project plant-manager-prod --since <ISO8601> --format json ...
```
Окно по умолчанию у CLI — 7 дней, поэтому для "последних полутора месяцев" везде нужен явный `--since 2026-06-15T00:00:00Z` (или актуальная дата минус 6 недель от текущей даты ресерча).

Графовые узлы для справки (см. `graph.py`): `fetch_context → act_agent ⇄ act_tools (цикл) → define_manual_actions → fetch_previous_issues → define_notifications → notify`.

## 1. Общая выгрузка данных за период

- Вытащить полный список ранов за 6 недель с `--include-metadata --include-io --include-feedback` (или `--full`), постранично через `--cursor`, отдельно по `run_type` (`chain`, `llm`, `tool`), чтобы не упереться в лимиты.
- Сохранить сырые JSON-выгрузки локально (например в `scratchpad`) — дальше все пункты работают по этому дампу, чтобы не бить API многократно.
- Посчитать базовые метрики по неделям: кол-во ранов, error rate, средняя/p50/p95 длительность полного цикла (`trace_id` верхнего уровня).

## 2. Все ошибки

- `langsmith run list --project plant-manager-prod --since <date> --error --include-io --format json` — полный список упавших ранов.
- Для каждого: `run_type`, имя узла, `error` текст, `trace_id` (чтобы поднять весь трейс целиком через `--trace-ids`).
- Сгруппировать ошибки по типу/сообщению (например: HA API 4xx/5xx, таймауты MCP, ошибки structured output/парсинга, исключения в Python-узлах типа `fetch_context`/`notify`).
- Для каждой уникальной группы ошибок — 2-3 примера трейсов с полным контекстом (inputs/outputs) для последующей диагностики root cause.

## 3. Основные задержки

- `langsmith run list --min-latency <N> --run-type chain --include-metadata` с разными порогами, чтобы найти хвост распределения (например top-20 самых долгих полных прогонов графа).
- Отдельно — задержки по типу узла: сравнить `llm` (`act_agent`, `define_manual_actions`, `define_notifications`) vs `tool` (`call_ha_api`, `get_all_devices`, MCP-тулы) vs `chain` (`notify`, `fetch_context`).
- Проверить, есть ли корреляция задержек с циклом `act_agent ⇄ act_tools` — считать среднее число итераций цикла на ран и смотреть, не улетает ли иногда в много итераций подряд (возможный признак агента "зацикливающегося" на попытках вызвать инструмент).
- Сравнить latency `call_ha_api` конкретно (это сетевой вызов к Home Assistant) — не деградирует ли он со временем или в определённые часы/дни.

## 4. Неэффективности в пайплайне

- Посчитать token usage/costs (`--include-metadata` даёт `token_usage`/`costs`) по узлам — какие LLM-вызовы самые дорогие и почему (возможно, `fetch_context`/промпт `act.py` тянет избыточный контекст).
- Проверить, сколько раз `act_agent` вызывает `call_ha_api`/`get_all_devices` за один прогон — есть ли повторные/избыточные вызовы одного и того же (например, опрашивает один и тот же device несколько раз за проход).
- Проверить `fetch_previous_issues` (48-часовое окно дедупликации issues) — не тянет ли слишком много данных, не дублируется ли с логикой `define_notifications`.
- Оценить, есть ли смысл кэшировать что-то между 4-часовыми запусками вместо полного re-fetch каждый раз.

## 5. Как отправляются нотификации + предложения по улучшению полезности

- Собрать все `notify`-раны (`--name notify` или по graph node) с их inputs/outputs за весь период — это финальный узел, который пишет `plants/update_agent_log` и шлёт push на `notify/mobile_app_iphone_2` (см. `graph.py:205-241`).
- Достать структурированный output `define_notifications` (Pydantic `Notifications`) для каждого рана — что конкретно агент решил отправлять и почему (какие issues он посчитал "новыми" относительно `fetch_previous_issues`).
- Посчитать частоту нотификаций по дням/неделям — совпадает ли с жалобой пользователя на "надоедливые нотификации" (см. TODO.md), и в какие моменты идёт всплеск.
- Проверить, есть ли повторяющиеся/дублирующиеся нотификации об одной и той же проблеме подряд несколько запусков — признак того, что dedup-логика в `define_notifications`/`fetch_previous_issues` работает не так, как задумано.
- На основе собранного — сформулировать конкретные предложения: группировка, порог значимости, снижение частоты повторов, более информативный текст (что реально нужно юзеру знать: какое растение, что случилось, что агент уже сделал/собирается делать).

## 6. Где неверная информация в нотификациях

- Сопоставить каждую отправленную нотификацию с реальным состоянием сенсоров на момент рана (через `fetch_context`/`get_current_status` output того же трейса) — искать случаи, когда текст нотификации не соответствует фактическим данным (например, ссылается на растение с уже устаревшим/`stale` показанием, или на неправильный zone/статус).
- Особое внимание на период до фикса stale-детекции в интеграции (до 2026-08-02) — в это время `get_current_status` мог отдавать замороженные значения как актуальные, и агент вполне мог формировать нотификации на основе 25-дневных устаревших данных о влажности почвы. Учитывая срок ресерча "полтора месяца" (примерно с середины июня), это накрывает и период до фикса, и после — стоит явно разделить анализ на "до фикса" / "после фикса".
- Проверить нотификации на предмет галлюцинаций/неточностей, не связанных со stale-данными: неверные названия растений, неверные числа (влажность/температура), несоответствие между reasoning в LLM-выводе и итоговым текстом уведомления.

## 7. Все неправильные действия агента

- Достать все `act_tools`/`call_ha_api` вызовы с их аргументами (`--include-io`) — какие именно HA-сервисы/команды агент вызывал (полив, свет, увлажнитель, термостат — см. допустимые действия в `prompts/act.py`).
- Сверить каждое действие с состоянием growth light/humidifier/watering до и после — было ли действие оправдано текущими данными на момент вызова (тот же trace).
- Отдельно собрать все случаи, когда `call_ha_api` вернул ошибку/неожиданный результат, но агент не отреагировал на это адекватно (продолжил как ни в чём не бывало, или зациклился).
- Это прямо пересекается с открытым вопросом из TODO.md "почему агент включает свет ночью" — искать все `act_tools`-вызовы, включающие grow light (`switch.horizontal_grow_light_control`/`switch.vertical_grow_light_control`), с timestamp вызова в локальном времени, и смотреть на промпт/reasoning, почему агент решил, что это уместно в это время суток.

## 8. Неправильные выводы агента

- Пройтись по structured outputs `define_manual_actions` (`ManualActions`) и `define_notifications` (`Notifications`) — искать случаи, когда вывод логически не следует из данных в `current_status`/`previous_issues`, переданных в контекст того же трейса.
- Проверить консистентность между `act_agent`'s reasoning (промежуточные LLM-сообщения в трейсе) и финальными structured outputs — не противоречит ли одно другому.
- Отдельно посмотреть на случаи, где `act_agent` решил вообще ничего не делать (0 tool calls) при том, что `fetch_context` показывал явно тревожные данные (red zone влажности и т.п.) — пропущенные действия так же важны, как неправильные.

## 9. Причины всех ошибок (root cause)

- Для каждой группы ошибок из п.2 — трассировка до первопричины: сетевая проблема HA (см. недавний инцидент с GW1200B и связанные регрессии из TODO.md), баг в MCP-сервере (`plants_mcp/tools/*`), проблема в самом графе (таймаут, неверная схема structured output, rate limit OpenAI), или инфраструктурная (Heroku dyno/scheduler).
- Явно проверить, коррелируют ли всплески ошибок по времени с известными инцидентами, которые уже задокументированы в этом репо: остановка GW1200B (~25 дней простоя, чинили 2026-08-01/02), три регрессии от stale-фикса (автоматизация/дашборд/сенсор, все от 2026-08-02), два pre-existing бага интеграции `plants` из TODO.md (`select.py`/`text.py` race condition, `services.yaml`).
- Если после исключения известных инцидентов остаются необъяснённые ошибки — выделить их отдельным списком как новые находки.

## 10. Все зависания (hangs)

- Искать раны без `end_time` при наличии `start_time` (не завершившиеся) и раны с аномально большой длительностью относительно медианы (по каждому `run_type` отдельно, т.к. LLM-раны и tool-раны имеют разный нормальный диапазон).
- Проверить, есть ли повторяющийся паттерн зависания на конкретном узле графа (например, всегда виснет на конкретном MCP tool call, или на конкретном LLM-узле) — сгруппировать по имени узла.
- Сопоставить зависания с 4-часовым расписанием Heroku Scheduler — если следующий запуск стартует поверх ещё не завершившегося предыдущего (нет ли recovery/timeout логики в `runner.py`), это отдельный риск для отметки.
